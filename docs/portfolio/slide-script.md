## Slide 5 — 핵심 질문과 가설 수정 과정

**제목**: 가설이 틀렸을 때, 결론을 바꿨습니다

**본문 (3단계 흐름도 추천: 원래 질문 → 발견 → 재정의)**:

1. **원래 질문**: 어떤 채널이 트래픽을 많이 데려오고, 실제로 사는/남는 유저를 데려오는가?
2. **원래 가설**: 성과 좋은 채널로 예산을 옮기자
3. **분석 중 발견**: 식별 가능한 유료 채널이 `google/cpc` 단 하나뿐 (전체의 5.3%)
4. **판단**: 유료 채널 간 예산 비교는 비교 대상이 둘 이상일 때만 성립 → 이 데이터로는 애초 목표(채널 재배분)를 검증할 수 없음
5. **결론 재정의**: "채널 재배분" → "채널별 투자 우선순위"

**하단 한 줄**: 데이터를 보기 전에 세운 결론을, 데이터가 허락하지 않을 때 바꾸는 것 — 그것이 분석가의 기본기라고 생각합니다.

## Slide 7 — 진짜 병목 발견 + A/B 테스트 설계

**제목**: 문제는 채널이 아니라 '구간'에 있었습니다

**본문**: 채널 대신 결제 플로우 자체를 들여다보니, `결제 시작 → 결제정보 입력` 구간에서 전 채널 공통으로 **40.8%**(9,715명 중 3,964명)가 이탈하고 있었습니다.

**A/B 테스트 설계 (표)**:
| 항목 | 내용 |
|---|---|
| 목표지표(OEC) | 결제완료 전환율 45.5% → 49.5% (MDE +4%p) |
| 필요 샘플 | 약 4,900명 (군당 2,440명) |
| 실험 기간 | 7~10주 |
| 가드레일 지표 | 주문금액 중앙값 하락 없을 것 / 결제 통과율 하락 없을 것 / 오류율 증가 없을 것 |

**하단 작은 문구**: 실험군이 없는 데이터이므로, 결과를 지어내지 않고 설계까지만 진행했습니다.

## Slide 8 — 데이터 품질 이슈를 직접 발견한 과정

**제목**: 이상한 숫자를 그냥 넘기지 않았습니다

**본문 (3개 항목)**:
- 구매 기록의 **15.9%**는 거래ID가 없어 중복 검증이 불가능함을 확인
- 유입 채널의 **18.5%**는 식별 자체가 불가능함을 확인
- 특정 유입 그룹(전체 5.5%)의 지표가 유독 높게 나온 원인을 추적한 결과, 크로스도메인 추적이 결제 단계에서 끊기며 발생한 **측정 오류**임을 역추적으로 확인

**하단 한 줄**: 지표가 튀는 그룹을 보면, 먼저 의심해야 할 것은 '효과'가 아니라 '측정'입니다.

## Slide 11 — 실데이터로 끝까지 갔을 때 드러난 문제들

**제목**: 목데이터에서 멈추지 않았습니다

**본문**: 목데이터 검증만으로는 절대 드러나지 않는 문제 4건을, 실제 API·실제 DB·실제 배포 환경까지 끝까지 밀어붙여 직접 발견하고 고쳤습니다.

**본문 (4개 항목, 번호 매기기 추천)**:
1. 접속 위치(IP)에 따라 통화 단위가 바뀌는 API 응답 → 실제 $19.99짜리 게임이 화면엔 "$29,800"으로 표시
2. 위 수정의 부수 효과로 날짜 형식이 바뀌며, 수집 데이터 전체가 조용히 스킵되던 버그
3. API 응답 하나의 오류가 전체 파이프라인을 죽이는 구조적 취약점
4. 프론트엔드-백엔드 간 통신 자체가 막혀 있던 설정 누락(CORS)
