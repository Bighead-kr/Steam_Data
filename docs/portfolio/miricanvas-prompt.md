# 미리캔버스 AI PT 프롬프트

(아래 전체를 그대로 복사해서 미리캔버스 AI 프레젠테이션 생성창에 붙여넣으면 돼)

---

데이터 분석가 신입 채용 지원용 포트폴리오 발표 자료를 만들어줘.

**목적/독자**: 한국 스타트업의 데이터 분석가(신입 또는 채용전환형 인턴) 채용 담당자가 서류/면접에서 보는 포트폴리오 발표 자료. 발표자는 지방대 컴퓨터공학과 졸업예정 4학년, 인턴 경험 없는 신입.

**콘텐츠 구성 원칙** (신입 개발자 포트폴리오 작성 가이드 기준):
1. 자기소개 & 핵심역량 요약 (3~4줄로 압축)
2. 프로젝트 중심 정리 — 프로젝트명 / 기간 / 역할 / 기술 스택 / 성과를 항목별로 명확히
3. 성과와 기여도 강조 — 문제 해결 과정과 수치화된 개선 결과를 중심으로
신입/대학생 기준이므로 "완성도"보다는 "문제를 어떻게 발견하고 판단해서 해결했는가"라는 **성장·판단 과정**을 강조해줘.

**템플릿 사용 방식**: 선택한 미리캔버스 템플릿의 기본 슬라이드 구성(표지·목차·섹션 구분·본문·마무리 같은 틀)은 그대로 따라가도 돼. 슬라이드 개수나 순서를 아래 내용에 맞춰 억지로 늘리거나 고정할 필요 없이, 템플릿의 자연스러운 흐름 안에 아래 내용을 배분해서 넣어줘. 다만 프로젝트가 2개이니 프로젝트별로 최소 1개 이상의 섹션(또는 섹션 구분 슬라이드)으로는 나눠줘.

**톤/스타일**:
- 두괄식 — 결론/핵심 수치를 먼저, 근거는 그 아래.
- 과장된 마케팅 문구·느낌표·감탄사 지양. 담백하고 분석가답게, 숫자와 근거로 말하기.
- "완벽하게 해냈다"는 톤 대신, 가설이 틀렸을 때 결론을 바꾼 과정, 데이터 품질 문제를 직접 찾아 고친 과정처럼 판단 과정 자체를 강점으로 보여주기.
- 컬러는 화려하지 않게 — 네이비/그레이/포인트 컬러 1개 정도의 차분한 데이터 중심 톤. 밝은 배경, 표·차트·숫자가 잘 보이도록 여백 충분히.
- 슬라이드당 메시지 하나. 텍스트 과밀 금지, 표나 숫자 강조 블록 적극 활용.
- 핵심 수치가 나오는 슬라이드는 큰 숫자/굵은 문장을 중앙에 크게, 근거는 아래 작게. 표·비교 내용은 표나 before/after 레이아웃으로.
- 아이콘·일러스트보다 표·숫자·간단한 도형(막대, 화살표) 우선.

## 자기소개 & 핵심역량 요약

지방대 CS 전공, 졸업예정 신입. 인턴 경험은 없지만, 실데이터로 GA4 채널 분석을 끝까지 완주하며 처음 세운 가설을 데이터가 부정하자 결론 자체를 스스로 재정의한 경험, 그리고 Steam API로 데이터 파이프라인을 수집→적재→서빙→배포까지 혼자 완주하며 실데이터 검증 과정에서 데이터 품질 버그 4건을 직접 찾아 고친 경험을 핵심 역량으로 제시.

## 프로젝트 1: GA4 유입채널 성과 분석 (메인 — 데이터 분석가 역량)

**프로젝트명**: GA4 유입채널 성과 분석 (Google Merchandise Store 이커머스 실데이터)
**데이터**: BigQuery 공개 GA4 이벤트 로그, 2020.11~2021.01(약 3개월, 블랙프라이데이 포함)
**기간**: 2026.08~09 (완료)
**역할**: 1인 분석 — 데이터 정의 확정, BigQuery SQL 분석, Tableau 대시보드 제작, A/B 테스트 설계까지 전 과정 단독 수행
**기술 스택**: BigQuery(SQL), Tableau Public
**산출물**: Tableau Public 대시보드(게시 완료), GitHub 쿼리 전체 공개, A/B 테스트 설계서

**문제 해결 과정 (두괄식)**:
원래 질문은 "어떤 채널이 트래픽을 많이 데려오고, 실제로 사는/남는 유저를 데려오는가?"였고, 원래 결론 가설은 "성과 좋은 채널로 예산을 옮기자"였다. 그런데 분석 중간에 유료 채널이 google/cpc 단 하나뿐임을 확인해, 애초 목표(채널 간 예산 재배분)가 이 데이터로는 성립할 수 없다는 걸 스스로 판단하고 결론의 방향을 "채널 재배분"에서 "채널별 투자 우선순위"로 재정의했다.

**핵심 결론(수치)**: "어긋나는 지점은 없었다." 채널은 볼륨만 최대 7배(Organic 37.7% vs Paid 5.3%) 차이 나지만, view_item 도달률(21.8~22.8%)·유저→구매 전환율(1.52~1.63%)·주문금액 중앙값($46~49)·주간 재방문율(5.04~5.26%) 등 유저 질 지표는 채널 간 전부 동일함을 4개 독립 분석으로 검증.

**진짜 병목 발견 + A/B 설계**: 채널이 아니라 결제 플로우 안의 특정 구간(결제 시작 → 결제정보 입력)에서 전 채널 공통으로 40.8%(9,715명 중 3,964명)가 이탈. 이를 근거로 A/B 테스트 설계: 목표지표(결제완료 전환율) 45.5%→49.5%(MDE +4%p), 필요 샘플 4,900명, 실험 기간 7~10주, 가드레일 지표 3개 명시. "데이터에 실험군이 없어 결과는 지어내지 않고 설계까지만 한다"는 원칙도 함께 언급.

**데이터 품질 이슈 직접 발견**: 구매 기록 15.9%는 거래ID가 없어 중복 검증 불가, 유입채널 18.5%는 식별 불가, 특정 유입 그룹(5.5%)은 추적 시스템 결함(크로스도메인 추적 끊김)으로 경로가 유실된 것임을 역추적. 지표가 튀는 그룹을 성급히 "효과"로 해석하지 않고 측정 오류를 먼저 의심한 사례.

## 프로젝트 2: Steam 저평가 게임 발굴 파이프라인 (보조 — 데이터 엔지니어링 역량)

**프로젝트명**: Steam 저평가 게임 발굴 데이터 파이프라인 & 웹앱
**기간**: 2026.09 (진행 중)
**역할**: 1인 개발 — 기획, ETL 파이프라인 설계, DB 설계, API/웹앱 개발, CI/CD 자동화, 프로덕션 배포까지 전 과정 단독 수행
**기술 스택**: Python, PostgreSQL(Supabase), FastAPI, GitHub Actions, Next.js/TypeScript, Render, Vercel

**문제 해결 과정 (두괄식)**: 목데이터 검증에서 멈추지 않고 실제 API·실제 DB·실제 배포까지 끝까지 밀어붙여, 목데이터로는 절대 드러나지 않는 문제 4건을 직접 발견하고 고쳤다: ①API 응답이 접속 위치(IP)에 따라 통화 단위가 바뀌어 $19.99짜리 게임이 "$29,800"으로 표시되는 버그 ②그 수정의 부수효과로 날짜 형식이 바뀌면서 수집 데이터 전체가 조용히 스킵되던 버그 ③API 응답 하나의 오류가 전체 파이프라인을 죽이는 구조적 취약점 ④프론트엔드-백엔드 통신 자체가 막혀있던 설정 누락.

**성과(수치)**: 파이프라인이 데이터를 모두 모은 뒤 한 번에 저장하던 구조를 배치 단위 저장으로 재설계. 실측 검증 — 2시간 46분짜리 실행이 외부 API 오류로 중단됐을 때도 이미 수집된 9,628건의 데이터는 안전하게 보존됨(기존 구조였다면 100% 손실). GitHub Actions 자동화 + Render/Vercel 프로덕션 배포 완료, 백엔드·프론트엔드 테스트 88개 전체 통과 유지.

## 마무리

두 프로젝트를 통해 보여주고 싶은 것: GA4 프로젝트는 가설이 틀렸을 때 결론을 바꾸는 분석적 판단력을, Steam 프로젝트는 실제 서비스가 굴러가게 만드는 엔지니어링 완주력을 보여준다. 둘 다 "완성도"보다 "문제를 발견하고 스스로 진단해서 고친 과정"에 초점을 둔다. GitHub·Tableau·Notion 링크와 연락처를 마무리 슬라이드에 배치.
